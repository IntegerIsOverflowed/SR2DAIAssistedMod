================================================================================
SpriteForm.cs - what was broken, how it was fixed, and why
================================================================================
Files touched:  cs/SpriteForm.cs  (the whole chrome), cs/Sprite.Text.cs (one
                engine bug), cs/ChromeDesign.cs (the designer's colour dialogs, new),
                EmptySR2DFormTemplate/ (new empty project).
Everything below was checked by running real windows on this machine (175% DPI,
2048x1536) and reading their pixels back, not by reasoning about the code. From
round six the reads are DPI-aware SCREEN grabs (PrintWindow renders a native
caption for a window that keeps an invisible real frame - section 20). The
harness lives outside the repo (D:\SR2Dlastdump\harness):
BarHarness.csproj compiles cs/*.cs plus a knob-driven form, so every property
below can be photographed:
  dotnet run -c Release -project harness/BarHarness -- --seed=7 --count=9 --skew=10 --shot=out.png
  harness\hit.ps1   - sends WM_NCHITTEST at the edges / corners, prints the HT code
  harness\dbl.ps1   - real SetCursorPos + mouse_event double click, compares window rects
  harness\winshot.ps1 - PrintWindow (flag 2) of any running process's main window
  harness\grab.ps1  - DPI-aware screen grab of a window rectangle plus its surroundings
  harness\crop.ps1  - crops / zooms one of those grabs nearest-neighbour, for reading pixels
  harness\styles.ps1 - decodes GWL_STYLE / GWL_EXSTYLE of a running window
  harness\anim6.ps1 - samples a window rectangle ~74x/second and prints every pixel
                       signature that changes: the minimize animation meter
  harness\Probe.cs  - pixel-counting tests against the engine (the shadow bug)
  harness\shots.sh  - one live screen grab per chrome variant + crop.ps1 + montage.ps1
  harness\pdiff.ps1 - counts the differing pixels of two same-size grabs: the A/B meter
  harness\extshot.ps1 - launches an app that has no harness knobs of its own (the
                       template) and grabs its real window pixels
  harness\wins.ps1  - every top-level window of a process (finds a stuck modal dialog)
  harness\evt.ps1   - pulls the exception of a crashed GUI app out of the event log
  harness\b.sh      - kill + dotnet build -c Release (the harness builds Debug by
                      default, so running the Release exe without this can shoot a stale binary)


--------------------------------------------------------------------------------
1. The chrome disappeared: "title bar covered with a rectangular something
   containing text", buttons gone, no icon.
--------------------------------------------------------------------------------
Was:   the bar was a strip with several children - a stripe Sprite, a caption
       Label, an icon box, a Dock.Fill filler label, the three buttons.
Bug:   SpriteForm's own teardown and any app that calls
       `Controls.Clear()` / rebuilds its child list disposed those children,
       because ControlCollection.Clear() disposes everything it removes. The
       form survived with a half-drawn bar: the leftover opaque filler label
       sat over the stripes showing the caption, which is exactly the
       "rectangular something containing text" that was reported.
Fix:   the bar is ONE control. TitleBarStrip owns a single cached Sprite and
       paints the background, the colour bars, the icon, the caption and the
       extra texts into it in one pass (RenderBar), then blits it. Its only
       children are the three caption buttons; even they are not required for
       the bar to look right.
Why:   one surface cannot be covered by a sibling, cannot be disposed behind
       your back by layout, and cannot get its z-order wrong. It also removes
       a class of flicker: the old bar repainted 4-6 controls per frame.
       Docked layout runs back-to-front through the child list, so the bar must
       have the HIGHEST child index to stay on top - OnControlAdded now calls
       bar.SendToBack() whenever app content is added on top of it.

--------------------------------------------------------------------------------
2. No window icon in the title bar.
--------------------------------------------------------------------------------
Was:   no icon was drawn at all.
Fix:   EnsureIconSprite() draws Form.Icon (or TitleIcon when set, ShowIcon=false
       hides the slot) sized with the bar (bar height - 8, clamped to 12..32),
       vertically centred, before the caption. A click in the icon's x range
       (iconClickZone) opens the window menu, a double click closes the form -
       native title bar behaviour.
Engine trap found: `icon.ToBitmap()` returns the icon's STORED frame (32x32) no
       matter what size you built the Icon with, so asking for
       `new Icon(ic, 16, 16).ToBitmap()` and blitting it overflowed the 24 px
       bar. Fixed by forcing the size in the engine instead:
       `new Sprite(bmp, SR2D.Transform.None, size, size)` resamples to exactly
       the slot. That is the shape of the fix, not a workaround - SR2D owns the
       rasterisation, so the icon scales with TitleBarHeight.

--------------------------------------------------------------------------------
3. The colour bars (the requested pattern).
--------------------------------------------------------------------------------
Bars are skewed rectangles running the full height of the bar: the top edge is
to the RIGHT of the bottom edge (as in the reference image), equal width,
random colours. Settings, all live (each setter touches the bar and it
re-renders on the next frame):
  StripeSeed            int, -1 (default) = a random seed picked when the form
                        is created (Environment.TickCount), same colours for
                        the life of the window; set it to a number to make the
                        palette reproducible.
  StripeBarWidth        px per bar (0..128, default 0 = the width comes out of the length) -
                        taken LITERALLY in every mode (round
                        nine: it used to be a maximum in the two text modes, which made the
                        painted bar narrower than the number in the property).
  StripeBarCount        used by FixedCount mode (0..4096, default 8). In the two text modes it
                        is the number the mirrored length is DIVIDED BETWEEN, and only while
                        StripeBarWidth is 0 - a positive width decides the count instead.
  StripeMode            None | CaptionLength (default) | AllTitleTextLength |
                        FixedCount. CaptionLength = one bar per character of
                        Text; AllTitleTextLength = one per character of the
                        caption PLUS every extra title text.
                        (ROUND NINE CHANGED WHAT THE TWO NUMBERS MEAN in the two
                        text modes: the length the run mirrors is the icon + text
                        block in pixels, a positive StripeBarWidth is that width
                        literally and the COUNT becomes ceil(length / width),
                        while width 0 divides the length between the mode's
                        count. FixedCount still takes both literally. See the
                        round nine section at the end.)
  StripeStyle           FullBars (default) | TopAndBottomLines - the same
                        parallelograms, but only a StripeLineThickness px band
                        at the top and the same at the bottom is painted, the
                        middle keeps the bar colour.
  StripeSkew            px the top of a bar sits right of its bottom. -1
                        (default) = half the bar height, which keeps the
                        slant constant as the bar grows.
  StripeColors          optional explicit palette (repeats, then alpha-forced
                        opaque); empty = the seeded HSL random colours.
  ShowStripes           convenience on/off switch.
Rendering notes: the bars go through SR2D's FillPolygon with pixel-CORNER
  coordinates and the engine fills rows [top, bottom), so 0..h covers the bar
  exactly and adjacent skewed bars share an edge with no seam and no
  half-transparent column. StripeLineThickness and the two line bands use
  SetLockRectXY to clip the same geometry instead of drawing different
  geometry - lines and full bars always agree.

4. Caption + extra texts, each with its own settings, shadow on by default.
--------------------------------------------------------------------------------
SetTitleTags(new TitleTag("DRAFT", 0xFF7FD4FF), ...) puts any number of texts
after the caption; each TitleTag has Text, Color, FontFamily, FontSize, Shadow
and ShadowColor, and Shadow defaults to true. Bar-wide knobs:
TitleTextColor, TitleTextFontFamily, TitleTextFontSize, TitleTextShadow
(default true), TitleTextShadowColor, TitleTextShadowOffset (default 1 px).
Both the caption and the tags draw through SR2D's DrawText with the shadow
overload, so a tag can opt out (Shadow = false) or use its own shadow colour.
The shadow exists so text stays readable over any bar colour, which is why it
is on by default rather than opt-in.
Bug found while doing this - real fonts were vertically clipped in a 24 px bar.
  The pixel font is 5x7 so it must be stepped up with the bar, but a SpriteFont
  size is already an absolute px em and the old code multiplied THAT by the
  same step (a 12 px font at scale 2 in a 40 px bar overflowed). TextScale()
  now splits the two: pixel font steps with the bar height, a real font draws
  at 1 when an explicit size is given and only the app default follows the bar.

--------------------------------------------------------------------------------
5. Borders: too thick, custom, no corner resize cursor, "transparent at full
   size", "garbage when scaling".
--------------------------------------------------------------------------------
Was:   eight separate grip Controls (4 edges + 4 corners) around the window,
       plus a thick fixed-colour frame.
Bugs:  a) the corner grips were sized 0x0 in several states, so the resize
          CURSOR never appeared on a corner (only the four edges worked);
       b) the grips were children with BackColor = Transparent, and in
          WinForms a transparent child paints the PARENT's background over its
          siblings - so the "invisible overlay" was visible and smeared the
          bar; that is the "transparent at full size" report;
       c) the grips were positioned from the old bounds during a live resize,
          which is the garbage seen while dragging an edge.
Fix:   all grip controls are deleted. The frame is now structural:
         - BorderColor (0xAARRGGBB) + BorderThickness (0..24, default 6) paint
           the frame as the FORM's own Padding + BackColor. No child control
           is involved, so nothing can be transparent over nothing, and there
           is nothing to mis-position mid-resize. An alpha of 00 (or
           thickness 0) = no frame at all, the content runs to the edge.
         - ResizeBandWidth (0..24) widens the grab without thickening the
           visible line (the classic thin-border-hard-to-grab tradeoff).
         - WndProc answers WM_NCHITTEST with HTLEFT/HTRIGHT/HTTOP/HTBOTTOM and
           all four HT*_LEFT/RIGHT corner codes, so the eight native cursors
           and the native resize loop come from Windows itself. GrabBand is 0
           when maximized or full screen, so a maximized window has no grab.
       BarCount/PatternWidth and the bar itself follow the new size through
       OnResize -> ApplyFrame + bar.Touch, which is why scaling is clean now.
Proof: hit.ps1 at pad 3 returns 13/14/16/17 on the four corners and 10/11/12/15
       on the edges (HTCLIENT at pad 10 = inside); the resize shots z1_grow
       (500 -> 750 wide) and z2_shrink (900 -> 400) plus the 260 px and the
       maximized 2048 px windows show a correct bar at every size.

--------------------------------------------------------------------------------
6. Double-clicking the title bar did not maximize / restore.
--------------------------------------------------------------------------------
Cause: TitleBarStrip is a Control, and Control raisesDoubleClick only fires when
       the ControlStyles.StandardDoubleClick bit is set (it is off for a plain
       Control, and Control.DoubleClick is an event - it cannot just be
       assigned). OnMouseDoubleClick was therefore never called. That is why
       the old handler existed but never ran.
Fix:   the bar's constructor calls
       SetStyle(... | ControlStyles.StandardClick | ControlStyles.StandardDoubleClick, true).
       Double-click now toggles maximize/restore; dragging a MAXIMIZED window
       restores it under the cursor with the grab point kept on the caption
       (Windows behaviour), right click on the maximize button is full screen.
Proof: dbl.ps1 (a real synthesized double click, not a call into the handler):
       800x500 -> 0,0 2048x1452 (working area, taskbar untouched) -> back to
       800x500.

--------------------------------------------------------------------------------
7. Constructor-order crash (found immediately, it blocked everything else).
--------------------------------------------------------------------------------
Bug:   the base Form constructor sizes the window, which calls the OVERRIDDEN
       OnResize; that touched `bar`, which is a readonly field not assigned
       until the derived constructor body runs -> NullReferenceException on the
       first `new SpriteForm()`, and the same for OnTextChanged.
Fix:   a `barLive` flag, false while the base constructor runs, set to true
       right after the bar is created and before it is added. OnResize,
       OnTextChanged, ApplyFrame, OnControlAdded and PlaceCorners-style layout
       all return early while it is false. The alternative (creating the bar in
       a field initializer) does not work: the bar needs `this`.

--------------------------------------------------------------------------------
8. ENGINE BUG (cs/Sprite.Text.cs) - a text background erased the drop shadow.
--------------------------------------------------------------------------------
Was:   Sprite.DrawText's shadow overload drew the shadow first and then handed
       the SAME bg colour to the plain overload for the main pass. The plain
       overload starts by filling its text box, and that box carries 2*scale
       padding - strictly larger than a 1-2 px shadow offset - so the fill
       painted the shadow away completely. Any caller using shadow + background
       got a shadowless, wrongly-padded box. This is a real engine bug, not a
       SpriteForm misuse.
Fix:   the background box is now filled BEFORE the shadow pass, and both text
       passes are made with bg = 0. Order: box -> shadow -> glyphs.
Proof: harness/Probe.cs counts pixels of each colour in a 120x40 target
       (bg = blue, text = white, shadow = green): fixed order gives
       "shadow px=104 bg px=1147 text px=46", the old order gives
       "shadow px=0" - the shadow was literally gone. The probe reproduces the
       old call order non-destructively rather than patching the engine down
       temporarily.

9. New empty project: EmptySR2DFormTemplate/
--------------------------------------------------------------------------------
What:  a .NET 10 WinForms desktop project that is as empty as Visual Studio's
       own "Empty App" template - Program.cs with the stock
       ApplicationConfiguration.Initialize() / Application.Run(new Form1()),
       Form1.cs + Form1.Designer.cs with only AutoScaleMode, ClientSize 800x450,
       Text = "Form1" - except Form1 derives from SpriteForm, so the window
       already has the SR2D chrome (bars, icon, caption with shadow, buttons,
       resizable border) with zero code written.
Why:  the repo's template/ is a working app with a SpriteBox canvas and a pile
       of controls; this is the "nothing but a form" starting point.
Two deliberate deviations from the VS template, both explained in
EmptySR2DFormTemplate/README.txt: AutoScaleMode is None (SR2D works in device
pixels; a scaled designer font desynchronises the chrome from the content), and
- since round two, see section 13 - Form1 is PUBLIC partial in both files, which
is what lets the Visual Studio designer open it at all. csproj mirrors
template/SR2DApp.csproj:
net10.0-windows, x64, nullable, implicit usings, allow unsafe, the latest
recommended analyzers, the engine compiled in from ../cs/*.cs, SR2D64.dll
copied next to the exe from ../native/bin/x64.
Verified: `dotnet build -c Release` succeeds with no warnings, the exe runs,
and winshot.ps1 captured an 800x450 window with the empty client area and the
full bar.

10. Incidental fixes made along the way
--------------------------------------------------------------------------------
* The pattern used to push the caption off-screen on a narrow window. The bar
  now clips the pattern to `width - ButtonsWidth() - TextGap`, so the caption
  and the three buttons always survive; DrawBars returns early at zero width.
* ButtonsWidth() is computed from Visible, so hiding a button (ShowMinimize-
  Button = false etc.) reclaims its room; each Show*Button setter touches the
  bar so the change is immediate.
* The bar's cache signature now includes the three button Visible flags and
  the app default font family / size, so those changes invalidate the cached
  render instead of showing a stale frame.
* CA2014 (stackalloc inside a loop): the bar's four polygon points are one
  stackalloc hoisted outside the loop and rewritten per bar.
* CS0649: TitleTag gained the (text, color, fontFamily, fontSize, shadowColor)
  constructor so ShadowColor is settable rather than left unassigned.
* CS1503: the frame colour is built with `unchecked((int)(0xFF000000u |
  (uint)borderColor))` - `int | uint` widens to long in C#, which does not
  convert back to Color.FromArgb's int implicitly.

11. Round two, item by item (all of these were re-measured on live windows)
--------------------------------------------------------------------------------
a) "title bar smallest size by default, with the smallest possible pixel font"
   MinBarHeight = 18 / MaxBarHeight = 64 now bracket TitleBarHeight, and the
   constructor starts the bar at 18 px instead of 26. The button glyphs used to
   be a fixed 12 px em, which is taller than an 18 px bar once the padding is
   counted, so LayoutBar sizes them with the bar: `glyph = clamp(bar.Height - 6,
   8, 20)`. The caption / tags already fell back to the 1 px PixelFont when no
   font is set, which is the smallest face SR2D has, and the default
   TitleTextFontSize is 0, so the bar renders at the pixel font by default.
   Evidence: def_bar.png (no --tbh at all) shows 18 px of bar with the icon, the
   bars, "SR2D64.dll" and three legible buttons; tall_bar.png is the same chrome
   at --tbh=40.

b) "text and icon in front of the coloured pattern, with a flag to put them after"
   RenderBar now paints the bars first and the icon + caption on top of them,
   starting at TextGap from the left edge. StripesBehindText (default true) is
   the flag: false restores the old order, where the pattern occupies the left
   part of the bar and the icon + caption start after it.
   Evidence: the default shot vs --behind=0 (behind0_bar.png) - same seed, the
   caption sits over the bars in one and after them in the other.

c) "when the icon is over the pattern, put it in a little rounded rectangle"
   IconChip() draws a FillRoundRect plate (70 % black) with a 1 px AA
   DrawRoundRect highlight under the icon, but only where the icon actually
   overlaps the pattern (`IconBackdrop && x < patternW`), and only while
   StripesBehindText is on. Radius and padding scale with the icon (pad =
   clamp(h/5, 2, 4)), so it stays a chip and never becomes a box at 40 px bars.
   IconBackdrop = false takes it away. Evidence: def_bar.png / tall_bar.png.

d) "the form must not resize to nothing"
   ApplyMinimumSize() derives a floor from the chrome itself - the three buttons
   + four text gaps + 80 px of pattern, and the bar + 40 px of content, plus the
   painted border twice - and is called from LayoutBar, ApplyFrame and the three
   Show*Button setters, so it follows every chrome change instead of being a
   constant. It only ever raises MinimumSize, never lowers one the app set.
   Evidence: --shrink=10 logs "MinimumSize={Width=184, Height=70}
   actual={Width=232, Height=70} barHeight=18 controls=2" and shrunk_frame1_x.png
   photographs the window at that floor with the icon chip, the caption and all
   three buttons intact. (232 rather than 184: a window that carries a real
   frame gets Windows' own minimum tracking width on top of ours - still a floor,
   just a slightly friendlier one.)

e) "the form still lacks the Windows 11 animations" - see section 12.

f) "the template project only opens in the code editor" - see section 13.

12. The Windows 11 animations: the window now keeps a real, invisible frame
--------------------------------------------------------------------------------
Was:   FormBorderStyle.None, i.e. no WS_CAPTION and no WS_THICKFRAME. DWM gave
       us rounding and a shadow (DWMWA_WINDOW_CORNER_PREFERENCE) and the
       WM_NCHITTEST band gave us the resize grips, but minimize / restore /
       close were hard cuts and there were no snap layouts.
First attempt (not enough): putting WS_SYSMENU | WS_MINIMIZEBOX | WS_MAXIMIZEBOX
       back on the window. Measured, it changed nothing - the window style went
       0x16010000 -> 0x160B0000 and the minimize was still one frame.
What actually works: keep WS_CAPTION | WS_THICKFRAME too, and take the whole
       non-client strip back into the client area, so the frame exists for DWM
       and is invisible for us:
         CreateParams      adds WS_SYSMENU | WS_MIN | WS_MAX (+ WS_CAPTION |
                           WS_THICKFRAME while NativeWindowFrame is true)
         WM_NCCALCSIZE     answers "the client is the whole window rectangle"
         WM_NCPAINT        swallowed - there is no strip left to paint
         WM_NCACTIVATE     forwarded with lParam = -1, so a focus change cannot
                           flash a native caption over the bar
       That is the standard recipe, and the measurement that justified it:
         harness\anim6.ps1 samples the window rectangle ~74x/second and prints
         every pixel signature that changes. A minimize Windows animates shows
         intermediate signatures; a hard cut shows one.
           --plain  (the old styles, 0x16010000) ....... 1 change, no in-between
           SpriteForm with only the menu bits ......... 1 change, no in-between
           SpriteForm + NativeWindowFrame ............. 2 changes (one in-between)
           --native (an ordinary captioned window) .... 3 changes
       and styles.ps1 confirms the window really carries
       0x16CF0000 = WS_CAPTION | WS_BORDER | WS_DLGFRAME | WS_THICKFRAME |
       WS_SYSMENU | WS_MINIMIZEBOX | WS_MAXIMIZEBOX.
Two consequences that had to be fixed on the way, both because the client area
now equals the window rectangle:
  * A maximized framed window is placed one invisible border OFF screen (2072 x
    1476 at -12,-12 for a 2048 x 1452 work area), which cut the icon and the
    buttons off. ClientInsideMonitor clamps the client rectangle back to the
    monitor's working area - max2_tl.png / max2_tr.png show the icon at x=0 and
    all three buttons inside the screen, and max2_br.png the taskbar still there.
    (WM_GETMINMAXINFO was tried first and does not work: WinForms computes the
    maximized rectangle itself from MaximizedBounds and SetWindowPos-es it, so
    the values written into that message are ignored. Measured, not assumed.)
  * Full screen used to be "maximized with MaximizedBounds = the monitor", and a
    framed window can never be maximized past the working area. ToggleFullScreen
    now places the window explicitly (Normal state, Bounds = the monitor or the
    working area) - fs log line: Bounds={X=0,Y=0,Width=2048,Height=1536}
    ClientSize={Width=2048, Height=1536}, identical to the old behaviour.
NativeWindowFrame = false gives the previous fully borderless window back, so
the trade is a switch, not a fork.

13. Opening a SpriteForm-derived form in the Visual Studio designer
--------------------------------------------------------------------------------
Was:   SpriteForm was `internal` with the [DesignerCategory("Code")] it inherits
       from Form. Both block the designer: the attribute is INHERITED, so VS
       opened every derived form in the code editor, and an internal base class
       hides every chrome property from the property grid even when the designer
       does open.
Now:   SpriteForm is public with [DesignerCategory("Form")], and
       EmptySR2DFormTemplate's Form1 is `public partial` in both files (the
       Designer.cs half has to change too, or the two halves disagree and the
       build fails with CS0262). The chrome properties are all public with
       Category / DefaultValue / Description, so they land in the property grid.
       Verified by build only - there is no Visual Studio on this machine, so
       the designer itself has to be confirmed on the dev box: open
       EmptySR2DFormTemplate, right-click Form1.cs -> View Designer (F7 cycles
       code and designer).

14. What is intentionally still true about this chrome
--------------------------------------------------------------------------------
The window carries a real frame and hides it (section 12). That buys the
animations, the shadow, the rounding and the snap layouts; what it still does
NOT buy: the native min / max / close BUTTONS (the bar draws its own, which is
the point of the chrome) and the caption Windows would have painted there.
A maximized window's client is clamped to the working area, so a taskbar set to
"always on top" cannot be covered by maximize - full screen places the window
instead. The minimum window size is a floor derived from the chrome, and a
framed window adds Windows' own tracking minimum on top of it.

15. Round six: resizing flickered
--------------------------------------------------------------------------------
Was:   every step of a drag rebuilt the bar's whole pixel pattern and let Windows
       erase the form's background before the paint. Measured over 20 grow + 20
       shrink steps with the shipped switch (harness --msg=1500 --smooth=0/1,
       counters inside the engine, see SpriteForm.ResetChromeCounters):
         barRebuild 20 -> 0      formBackgroundPaint 80 -> 39
       WM_SIZE (40) and WM_PAINT (39) are the same on both sides, so the message
       traffic did not change - only what happens per paint.
Now:   SmoothChrome (default true) does two things. SetStyle(OptimizedDoubleBuffer
       | AllPaintingInWmPaint) makes the form fill its background in the buffer
       instead of erasing on screen - that is the 80 -> 39, one fill per WM_PAINT
       rather than erase plus paint. And the bar's pixel buffer is allocated
       oversized (1.5x the strip, capped at 4096 px) and left-anchored, so
       dragging the edge paints into buffer that already holds the pattern instead
       of re-rendering it - that is the 20 -> 0.
       Compat: SmoothChrome = false is the previous path, a rebuild per step.

--------------------------------------------------------------------------------
16. Round six: losing focus turned the chrome into "default form graphics"
--------------------------------------------------------------------------------
Was:   on deactivation the bar was replaced by a grey native caption with three
       native buttons. Round five had concluded that WM_NCACTIVATE must be
       forwarded to DefWindowProc with lParam = -1, because that lParam is
       documented as "do not redraw the non-client area".
Found: on this Windows build (10.0.26100) that is not what the default handler
       does with an invisible frame. It repaints exactly the strip
       WM_NCCALCSIZE had given back to the client, i.e. the whole bar. The
       measurement is the A/B switch SpriteForm.NcActivateProbe: 0 replays the
       pre-fix answer verbatim, 1/2 refuse the message. Same window, same
       arguments, focused shot vs blurred shot, DPI-aware screen grabs of the
       live window compared with harness/pdiff.ps1:
         --ncprobe=0   40833 differing pixels of 472160   (the caption is back)
         --ncprobe=2       3 differing pixels of 472160   (edge noise; identical)
Now:   WM_NCACTIVATE is answered without passing the activation change down
       (m.Result = 1) and the bar is marked dirty. The window still gets its
       WM_ACTIVATE, still minimizes / maximizes / snaps, and the chrome no longer
       changes when something else takes the foreground.

17. Round six: the BackColor set in the designer never reached the screen
--------------------------------------------------------------------------------
Was:   "I changed the form colour in the designer, at runtime it is the same dark
       grey." ApplyFrame() painted the border band by writing the FORM's BackColor
       to the border colour, and it ran after InitializeComponent - so whatever
       colour was set in the designer was overwritten before the first paint.
       The template's designer file even looked innocent: its BackColor is
       Color.FromArgb(46, 52, 60), which is the same 2E343C the border colour
       defaults to, so the lost value and the surviving one were indistinguishable.
Now:   ApplyFrame only sets Padding; the band is painted in OnPaintBackground from
       BorderColor (section: the border is the form's own painting since round
       four). The A/B is SpriteForm.BackColorProbe: 0 replays the old write, 1 is
       shipped. Harness --backprobe=0/1 --backcol=20A020 --nolabel, same window,
       client-area patch compared: 59800 of 59800 pixels differ - with the old
       path the whole client reads 2E343C (the border colour), with the shipped
       path it reads 20A020 (the requested colour).
       End to end: EmptySR2DFormTemplate's Form1.Designer.cs was set to
       BackColor = Color.FromArgb(32, 160, 32), built and photographed with
       harness/extshot.ps1 - the client area is green at runtime (then reverted).
       Note what this does NOT change: a docked child that paints its own
       background still covers the form's. That is normal WinForms, and the
       template's client area is empty by design.

18. Round six: the SR2D controls were not in the toolbox
--------------------------------------------------------------------------------
Was:   "in a form-template project the SR2D controls do not show in the toolbox,
       they did show in an empty-form project where I added the cs files".
Found: the toolbox only lists PUBLIC Control types. SpriteBox and every control
       derived from it were internal, so they were never candidates - the case
       that appeared to work was an empty-form project where the classes were
       compiled into the same assembly and used from code, not dragged.
Now:   the whole surface a designer can touch is public: SpriteBox,
       SpriteControlBase, SpriteClickable, SpriteRangeControl, all 25 controls,
       Sprite, SpriteFont, PixelFont, Effects, SR2D, RenderEventArgs, ControlText,
       TextRun and the ~50 enums in their public signatures - 44 files, 258 type
       declarations. CS0050/CS0051/CS0053 (a public member cannot use a less
       accessible type) is what closed the list, and the loop that applied it is
       harness/publicize.sh: build, take the type named left of "is less
       accessible", flip it, repeat until the build is clean.
       Two things stayed internal on purpose: SpriteForm.Point (an engine pixel

19. Round six: the colour bars got the rest of their surface
--------------------------------------------------------------------------------
       StripeOffset (int, -2048..2048) slides the whole pattern along the bar.
       StripeAlignment (Left / Center / Right, + WithText since round nine)
       anchors the pattern, so a pattern
       shorter than the bar can sit at either end or in the middle.
       StripeBrightness (int, 0..300 %) scales every bar colour in place; it is
       applied to the palette, so it also multiplies a custom colour list.
       StripeColorList (string, "FF3B82F6,FFEF4444,Red" - the designer-visible
       entry) and StripeColors (int[], [Browsable(false)], the same as pixels)
       replace the random palette; StripeSeed still decides the order and the
       random case, and an empty list restores it. The string takes the same
       forms ArgbColorConverter accepts (AARRGGBB, #RRGGBB, 0x..., a 6-digit
       value gets an opaque alpha) plus System.Drawing colour names; a token that
       is neither is skipped rather than turning into black.
       The getter of that property is a bug that only the designer could hit, and
       it is worth writing down: it was string.Join(",", int[]), i.e. DECIMAL
       ("-13749188" for FF2E343C), while the setter parses HEX. Visual Studio
       reads the value, writes it into InitializeComponent, and the next load
       dropped every colour - the palette silently vanished after one save. The
       getter now emits the 8-digit hex the setter reads. Measured with
       harness --design, which does set -> get -> set on five inputs through
       TypeDescriptor (the same path the designer uses) and prints stable=True
       for each; the old decimal form, fed through the same setter, keeps 0 of
       2 colours. And --pal (the int[] path) vs --pallist (the string path)
       produce byte-identical screen grabs, so the two entry points are the same
       pixels.
       StripeMode.CaptionLength and .AllTitleTextLength now measure the TEXT IN
       PIXELS, not characters: the pattern stops at the right edge of the last
       glyph, so the last bar reaches the last symbol (the old behaviour counted
       characters against the pixel font's fixed cell, which drifted as soon as a
       real font or a tag was involved).
       TitleTextDarken (None / Smooth / PerStripe) with TitleTextDarkenStrength
       (0..100) and TitleTextDarkenFeather (0..256 px): where the caption sits on
       the pattern, the bars lose brightness - Smooth as a gradient across the
       text rectangle, PerStripe one decision per bar so each bar stays flat.
       All of these are in the bar's cache signature, so setting one repaints.
       Photographed per variant in harness/shots.sh -> variants.png (17 rows:
       base, offset, align center / right, brightness 40 / 200, palette as int[]
       / as string / as names, caption length, all-text length, darken smooth /
       per stripe, a real caption font, and the three BackColor A/B shots).

  WHAT THE REPORT SAID   "with stripe mode = caption length, width of bars not equal of width that
                    set up in property", and then the model the user wanted, spelled out: the number
                    of bars is whatever covers icon + caption (or icon + all the texts), the whole
                    coloured stripe can be centred on that icon + text block, and the two pairings -
                    custom width / auto amount and custom amount / auto width ("mode caption length,
                    I set up number of bars 10, width of 1 bar = length / number_of_bars").
                    Round eight answered the length complaint by capping the WIDTH: in the two
                    text-mirror modes a positive StripeBarWidth became a maximum and the bars were
                    narrowed to their share. The template's own saved values (CaptionLength +
                    StripeBarWidth = 10 over a 46-character caption) therefore painted 50 bars of
                    6,54 px - the right run, the wrong bar - and this is the report. The two rounds
                    are the same argument seen from the two ends: the length and the width cannot
                    both be honoured against a mirrored text, so one of them has to be derived. The
                    user's answer is that the WIDTH is the number he typed, so the COUNT moves.

  PLANBAR NOW   StripeBarWidth is literal in every mode. In CaptionLength / AllTitleTextLength the
                    count is ceil(budget / width); with the width at 0 the budget is divided between
                    the mode's count instead (BarCount: one bar per caption / per every-text
                    character). FixedCount is the mode where both numbers are the user's own and
                    nothing is derived - the escape hatch for "I want exactly N bars of exactly W px
                    even if it runs past the text". WidthCapProbe (harness --widthcap=1) is the A/B
                    that reproduces round eight; the shipped default flipped to 0, so the probe now
                    has to be asked for explicitly, and --widthcap=1 prints exactly the old plan:
                          plan, template caption, StripeBarWidth=10   shipped:  count=32 barW=10 runW=329
                                                                        probe 1:  count=50 barW=6  runW=327
                    The budget is not the glyph run any more: blockW = (icon + gap when a chip is
                    drawn) + the texts the mode counts, and with StripeAlignment Left the run also
                    has to reach past the block's own 8 px margin. --geom measures the result off a
                    screen grab, glyph by glyph:
                          mirrored block 8..327, run 8..327, painted silhouette off by 0 px
                          --mode=fixed --count=10                    count=10 barW=32, "one bar per 32,70 px of text"
                    Note that the -2 px of the earlier cells is the grab's own rounding at the bar
                    rows this caption lands on, not a systematic shortfall - tpl / tpl_wt show the
                    same plan painted at 0 px off.

  CENTRED ON THE BLOCK   StripeBarsAlign.WithText. Left pins the run to the bar's corner (so it
                    reads as growing out of the corner and reaches the last glyph); Center / Right
                    place it in the bar, which is what made it drift away from the text on a wide
                    window; WithText centres it on the block, the same margin past the icon as past
                    the last glyph. With StripesBehindText off the texts sit AFTER the pattern, so
                    the two are laid out as one centred group instead. Measured, same caption:
                          block 8..327 (centre 167), run 8..327 (centre 167): centre delta 0 px,
                          0 px of colour left of the icon, 0 px right of the last glyph
                    --align=center on the same window is centre delta 242 px - that is the difference
                    the new value is for, and it is why the default stays Left.

  THE GRID'S COLOUR CELLS   "when i edit form in the designer, BackColor / ForeColor have this color
                    rectangle thingy and the R G B values, and pressing arrow down opens a list of
                    colors - but other color properties like BorderColor have just a HEX text field".
                    BorderColor always had the "..." dialog; what it did not have was the CELL.
                    ArgbColorConverter (cs/ChromeDesign.cs) now answers the three questions the
                    property grid asks a converter, so an int ARGB property is drawn and edited like a
                    System.Drawing.Color one: GetPaintValueSupported (the swatch),
                    GetStandardValuesSupported (the drop-down arrow) with the named-colour list and
                    GetStandardValuesExclusive = false (pick from it, or keep typing), and ConvertTo
                    returning what a Color returns - the name when the value has one, otherwise
                    "[A=255, R=46, G=52, B=60]". Reading back accepts that display text plus every
                    other spelling, so nothing you can see is untypeable:
                          FF2E343C / #2E343C / 0x2E343C / 2E343C -> FF2E343C
                          4278190080 -> FF000000    4294901760 -> FFFF0000   (decimal ARGB)
                          Red -> FFFF0000   SteelBlue -> FF4682B4   Transparent -> 00FFFFFF
                          [A=255, R=46, G=52, B=60] / [R=46, G=52, B=60] / Color [R=46, ...] -> FF2E343C
                    The grid is on another machine, so this is proved through the same descriptor the
                    grid reads (harness --gridprops), which prints converter / dropdown count /
                    exclusive / swatch / editor / the text the cell shows for all six properties.
                    BackColor itself reports converter=ColorConverter dropdown=175 swatch=True - the
                    numbers to compare the int properties against are now 157 and True, and the one
                    difference left is the 18 named colours that only exist as SystemColors roles.

  THE PALETTE IS ALREADY INT-CACHED   "except StripeColorList ... would be nice if i could use
                    integers and HEX, but cache it to ints for performance, if it's not yet". It was:
                    the setter parses the string into StripeColors (int[]) and the paint code reads
                    only that array, so a resize or a frame costs no conversions; the string is the
                    editor's text and the getter's round trip (the decimal-getter bug of round six is
                    what made that worth writing down). What it could not do was take a plain integer
                    per entry - ParseColors delegated to ArgbColorConverter, which read hex only - so
                    it does now, same TryParse as every other colour field, and the documentation says

  CONTROLS INHERIT THE FORM NOW   "controls added to the form (as example sr2d controls) don't
                    inherit colors from form ... they don't inherit background color. i assume
                    controls should". They did not, for a reason that is in the constructor:
                    SpriteControlBase sets BackColor = DefaultBack (0x202428) so a knob stays dark on
                    a light form, and a WinForms control that has had BackColor set stops being
                    ambient - the chain broke at our own line. The container case was already handled
                    (_backExplicit / AdoptBackColor / ChildBackColor / PushBackColor), the FORM case
                    was not, and the designer made it permanent: InitializeComponent writes
                    "BackColor = Color.FromArgb(32, 36, 40)" - exactly that default - for every
                    control you drop, so even the container path could not reach it afterwards.
                    Three pieces fix it: SpriteForm hands its colour to the SpriteControls parented
                    directly on it (OnBackColorChanged), a control asks the window it is put on when
                    its parent changes, and the SR2D default no longer counts as a choice -
                    ShouldSerializeBackColor returns false for it, so the grid stops writing the line
                    at all, and ResetBackColor clears the flag so the property menu puts the control
                    back on the ambient colour. An untouched form hands out NOTHING (its BackColor is
                    still SystemColors.Control): a form nobody coloured must not turn every dark
                    control on it light. Harness --inherit walks the matrix:
                          untouched form      plain / designer-default 0x202428, explicit Red stays
                          form -> 2E343C      plain, designer-default, panel all follow; the label
                                              inside a sunken panel takes the panel's face (35,40,46)
                          form -> 14 5A 1E    everything follows again
                          form -> Control     the controls revert to 0x202428, Red never moved

  WHY AN INTERFACE, NOT THE TYPE   The obvious implementation was `if (Parent is SpriteForm f)`, and
                    it does not compile: tests/cs/ctlrun builds its own file list and leaves
                    SpriteForm.cs out, standing in for WinForms with hand-written shim types in
                    Fake.cs. So the hook is internal IControlFaceSource { Color? ControlFaceColor; }
                    declared in cs/SpriteControls.cs and implemented by SpriteForm, which keeps the
                    control file independent of the chrome (in ctlrun nothing implements it and the
                    test form's ambient colour simply never applies - the headless suite is not where
                    this behaviour is checked). The same shim is why SpriteControlBase.ResetBackColor
                    needed Fake.Control to declare the member at all (CS0115 there, CS0507 against
                    real WinForms, where it is public virtual): the fake API surface has to match the
                    real one for an override to bind, and adding the declaration is the fix, not
                    dropping the override.
